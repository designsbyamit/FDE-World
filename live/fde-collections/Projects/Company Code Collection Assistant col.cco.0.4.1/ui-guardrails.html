Collection Assistant UI Guardrails

Reusable layout and interaction rules extracted from the established Collection Assistant worklist and Customer 360 prototypes. New features—including Company Code—should fit these patterns with the smallest possible visual and behavioural change.

Baseline: SAP Horizon · SAP 72 · UI5 Web Components · cozy density

1. Page frame

Global shellUse the shared app-shellbar at the top. Keep product title, navigation/menu affordance, help, and profile treatment consistent across pages.
Sub-headerBelow the shellbar, use a white sub-header with breadcrumb/context on the left, page/customer title, compact metadata, and primary page actions on the right.
SpacingUse the established rhythm: approximately 2rem horizontal page padding, 1.5rem main content padding, and generous section separation. Do not introduce dense edge-to-edge feature panels.
Visual languageUse SAP design tokens for background, borders, text, link, status, information, and shadows. Prefer white cards on the SAP background with light borders and modest radius.
TypographyUse SAP 72. Page titles are prominent; section titles are semibold; supporting labels and metadata are smaller but readable. Keep new feature copy at least 14px where it is user-facing.

2. Worklist pattern

Shellbar→Page title/subtitle→Filter area→Toolbar→UI5 table
  • Keep filters in a white, full-width filter band directly below the page header.
  • Use labelled fields, UI5 inputs/selects, and an emphasized Go action; secondary actions remain transparent.
  • Support filter collapse and pin affordances in the established centered control row.
  • Use a UI5 table with clear column headings, pop-in behavior, sticky/right-aligned actions where needed, and link-style navigation.
  • Use tags for priority/status; do not rely on color alone for meaning.
  • Use lightweight popovers for ageing detail, priority explanation, and other contextual information.
Company Code rule: Keep Customer as column 1, Priority as column 2, and Company Code as column 3 and in Adapt Filters. If one customer spans multiple codes, show one parent row with Customer ID, Customer Name, Priority, and Actions. Expanded child rows leave those customer-level cells blank and show only Company Code and code-specific measures.

3. Customer 360 pattern

Identity headerShow breadcrumb, customer name, customer ID, key contact, and priority in the established compact header. Keep a Close/back action in the header action group.
Main/side layoutUse a scrollable main column and a fixed right rail of approximately 450px for Account History or Agent content. Separate the rail with a left border.
AI insight cardPlace Insights and Recommendations near the top of the main column in a white card. Explain the reason, relevant exposure, and next action in plain language.
Account contentUse a card with a UI5 tab container for Account Overview, Open Items, Payments/Reimbursements, and Disputes. Tables inside tabs get a compact toolbar and settings action.
KPI tilesUse a three-column KPI grid inside the account card. Keep values prominent, labels below, and card treatment consistent. New dimensions should add or replace tiles without changing the card grammar.
Right railKeep Account History and Agent views as tabs in the side rail. Do not move history into a full-page route for a new feature.

4. Overlay and panel patterns

PatternUse forGuardrail
Right slide-in panelEmail compose, notes, call script, consequential action workflowAnchor to the right edge; preserve page context; use a header, scrollable body, and footer actions. Existing prototype uses roughly 660px width with a shadow and rounded top-left corner.
PopoverAgeing breakdown, priority explanation, small filters, email previewKeep contextual and lightweight; anchor to the triggering control; avoid using it for long forms or multi-step work.
DialogSettings, feedback, discard/confirmation, focused decisionUse only for a bounded decision. Provide explicit Cancel/Confirm or Close actions and keep width close to existing patterns.
ToastNon-blocking completion feedbackUse after a successful low-risk action; do not use it as the only confirmation for consequential writes.
Do not invent a new drawer, bottom sheet, full-screen modal, or floating command bar when an existing slide-in panel, popover, or dialog covers the interaction.

5. Control placement and behavior

  • Primary page actions sit in the top-right header action group or at the bottom-right of a slide-in panel.
  • Use emphasized buttons for the primary action; use Default or Transparent for secondary actions.
  • Use transparent/link-style actions inside tables and cards; avoid solid button clutter in repeated rows.
  • Use overflow/settings icons for secondary configuration, with tooltips.
  • Keep filter, sort, export, and table settings in toolbars—not mixed into data cells.
  • Maintain keyboard focus, visible state changes, and text labels/tooltips for icon-only controls.
  • For AI explanations, make the reason discoverable from the priority/status control without navigating away.

6. Company Code decision guardrails

DecisionUse this patternDo not do this
Customer identityCustomer ID + Customer Name remain stable across company codes.Do not create a different customer row/name for each code when the underlying customer is the same.
Worklist rowOne consolidated parent row; show Multiple (n) and expand into child rows.Do not fragment one customer into unrelated top-level customers solely because the code differs.
Financial measuresShow code-specific amounts in child rows/details; show consolidated values in the parent with reporting currency and exchange-rate context. When display and native currency differ, keep native value as secondary text.Do not add incompatible currencies or show a consolidated total when its conversion basis is unavailable.
Customer 360 scopeUse an inline scope control such as All Company Codes / code values; keep the page shell and layout unchanged.Do not create separate Customer 360 pages per company code.
Insights and priorityKeep Insights and Priority at customer level; explain company-code contributions in the existing detail or popover patterns.Do not recalculate priority or visually imply a separate customer identity per code.
KPIs and historyUse compact scope badges to distinguish Customer level, All codes, and Code n within the existing cards and history list.Do not split the page into duplicate customer/code layouts.
ActionsMake the selected company code explicit inside the existing right slide-in action panel; retain existing approval/recipient patterns.Do not introduce a new action surface just for Company Code.

7. Change review checklist

  • Required Does the change preserve shellbar, sub-header, main/side layout, card grammar, and control placement?
  • Required Does a customer spanning codes still appear as one customer identity?
  • Check Are new overlays one of the established panel, popover, dialog, or toast patterns?
  • Check Are summary and code-specific values clearly separated?
  • Avoid Does the change add a new navigation model, persistent floating control, or full-screen interruption?
  • Check Are unresolved backend/data assumptions visible as annotations rather than disguised as final UI behavior?
