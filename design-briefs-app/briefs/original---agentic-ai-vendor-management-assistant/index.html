Problem Statement

Sanofi wants to move from a fully manual Vendor Master Data (VMD) handling model to an agent-orchestrated lifecycle. Today, every onboarding, maintenance edit, and retirement action requires direct human handling by the VMD team — regardless of the nature or risk level of the change.

The target is 60–80% touchless processing for low-risk changes, freeing the VMD team to focus on changes that require genuine human judgment.

Current State Pain Points
  • Cycle time averages 5–7 business days end-to-end — driven by manual queuing and handoffs at every step.
  • 0% touchless automation — every request touches a human, regardless of how trivial the change.
  • Risk judgment is made manually by individual reviewers with no enforced standards, leading to inconsistent decisions across the team.
  • Approval routing is ad-hoc — the reviewer decides where to send a request based on personal judgment, not a defined ruleset.
  • There is no self-service channel for suppliers — changes are submitted by email with no acknowledgement, no tracking, and no feedback loop.
  • Manual ERP updates introduce delay and error risk after approval, adding a further bottleneck before the change takes effect.
  • There is no systematic audit trail — producing a reliable record for SOX reviews requires manual reconstruction from emails and spreadsheets.
Objectives

Phase 1:

  1. Achieve 60–80% touchless processing for low-risk vendor maintenance changes.
  2. Replace manual risk judgment with a consistent, enforced risk classification model.
  3. Automate approval routing based on risk level — eliminating ad-hoc human routing decisions.
  4. Enforce compliance through systematic audit logging and data retention (SOX: 5-year retention on VMD change records).
  5. Reduce VMD team workload on low-risk requests so they can focus on changes requiring genuine human judgment.

Deferred:

  1. Vendor onboarding (Phase 2)
  2. Vendor retirement / deactivation (Phase 3)
Personas
VMD Team Reviewer
Internal · Accounts Payable / VMD
Current state
Receives all change requests regardless of risk level, manually applies risk judgment, routes for approval, and executes updates in ERP.
Pain point
Spends significant time on low-risk, routine changes. Risk judgments are inconsistent across the team.
Future state
Low-risk changes handled automatically. Reviewer focuses only on exceptions and high-risk items requiring human judgment.
Supplier / Internal Requester
External supplier or internal user
Current state
Submits change requests via email, portal, or form. Has no visibility into status after submission.
Pain point
No feedback loop — request disappears into the VMD queue with no acknowledgement or tracking.
Future state
Clear submission experience with confirmation and visibility into what happens next.
Manager / Approver
Internal · Account or Category Manager
Current state
Receives ad-hoc approval requests for medium-risk changes via Outlook email. No structured task management.
Pain point
No context provided with approval requests. No SLA tracking or escalation if no response.
Future state
Receives structured approval tasks with full context. Can approve, reject, or delegate from a single screen.
Admin / Compliance Officer
Internal · Compliance or Procurement
Current state
No systematic audit trail. Rule ownership is informal — changes to risk classification rules are not versioned or governed.
Pain point
Cannot produce a reliable audit record for SOX reviews. Cannot confidently answer "who changed what and when?"
Future state
Access to a full, exportable audit log. Ability to view and update risk classification rules with version history.
Constraints
  • SAP MDG is the system of record — all approved changes must be written back. API ownership and write-back approach are unresolved.
  • Whether the target ERP is ECC or S4HANA is unconfirmed — this significantly affects the integration approach.
  • Bank account verification depends on Trustpair (external tool). Credentials, contracts, and sandbox access not yet confirmed.
  • Sanofi uses Elementum as their S2P platform. API ownership and appetite to migrate to SAP S2P are open questions.
  • All vendor master data changes must be logged with actor, timestamp, and field-level before/after values.
  • Minimum 5-year retention on VMD change records (SOX requirement).
  • Sensitive data changes require a second approver — not solely the requester.
  • 90-day execution window referenced as the target once scope and architecture are signed off.
Open Questions
  • Where does data from Sanofi's S2P system (Elementum) currently reside? — Determines the intake API and data source for the agent.
  • Who owns and manages the APIs from S2P to the agent layer? — Blocks technical integration planning.
  • Does human-in-the-loop approval live in the S2P system or within the agent layer? — Determines where approval logic is built and maintained.
  • After SAP VMD update, who owns the status sync back to S2P — SAP or Sanofi APIs? — Affects write-back architecture and ownership.
  • Is there appetite to migrate from Elementum to SAP S2P? If yes, by when? — Could change the integration target entirely.
  • Is the target ERP system ECC or S4HANA? — Directly affects the MDG API approach.
  • What is the risk classification logic, and who owns it — VMD, Procurement, or Compliance? — Ownership determines who governs rule changes over time.
  • What percentage of total maintenance requests are low-risk today? — Required to validate the 60–80% touchless target.
  • Which specific fields are approved for auto-execution in Phase 1? — Determines the scope of automation and the risk classification table.
  • What metric defines success for the maintenance MVP — cycle time, % touchless, or workload reduction? — Needed to set measurable acceptance criteria.
  • Do vendors have a unique identifier (e.g. vendor number) that can be used to scope portal access to their own records only? — Required for supplier portal authentication model.
  • Is Trustpair already contracted, or will it be contracted before Phase 1 go-live? — Bank verification cannot be built without confirmed access.
  • Will the AP team be the initial reviewer population with no complex approval hierarchies in Phase 1? — Affects the routing model and the number of approver roles to design for.
  • Are risk classification rules stable enough for Phase 1 that no dynamic rule-editing UI is required? — Determines whether a rules management interface is in scope.

Scope for Design
Vendor field change (low risk fields only)
Supplier edits low-risk fields in the self-service portal. The agent classifies the change, validates it, and applies it to SAP automatically without human review. Supplier receives a confirmation with the outcome.
Vendor field change (all fields)
Supplier edits fields that trigger a review. Medium-risk changes are routed to the account manager for approval; high-risk changes go to the VMD reviewer queue. Each approver reviews the full change diff and agent assessment, then approves, rejects, or escalates. The outcome is applied in SAP and communicated back to the supplier.
Risk rules management
Admin or compliance officer views and edits the risk classification ruleset that governs how field changes are routed. Changes to rules are versioned with author and timestamp; previous versions are retained for audit purposes.
Audit log and compliance reporting
Compliance officer queries the full VMD change log, filters by vendor, date range, or change type, and exports a structured report for SOX review.
